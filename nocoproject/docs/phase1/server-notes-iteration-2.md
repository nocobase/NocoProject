## 3. 设计要点

- **审批只经接口**：业务侧（`issue.status.ts`）在转换前调 `approvals().gate(input, tx)`；批准时网关通过 `ApprovalHooks.applyTransition` 回到任务服务。状态被任何路径改变后，`services.ts` 组合的提交前钩子先调 `cancelStale`，再交给通知模块；取消产生的事件在下一轮被通知模块处理。替换官方实现时只换 `approval/` 与 `services.ts` 里的一行。
- **状态写入集中**：`writeStatus` 统一写修订号、活动、终态放行与事件；Agent、系统（PR 合并）、批准三条路径共用。
- **webhook 事务**：投递记录与处理同一事务，重复投递靠唯一约束识别；GitHub 请求都在事务外做（手动关联、刷新先拉取再开事务）。
- **密钥**：只在 `crypto.ts` 解析；Provider 读配置 `nocoproject.secretKey` 与 `auth.secret` 传入；测试用固定密钥；解不开的密文按"未设置"处理而不是让请求失败。
- **AI 解析器**：`AiAgentFactory` 把 AI 员工插件缩成两件事（建会话、建无工具 Agent），测试用假工厂；本机没有 LLM，线上走启发式。
- **软删除**：只在查找层过滤（`findIssue`、`issuesByIds`、列表、子任务、阻塞、计数），任务行本身不暴露 `deletedAt`。

## 4. 已知缺口

- 迁移文件在开发库执行后又做过一次 prettier 格式化（只有换行），`db apply` 会提示 checksum 变化：需要主会话在终端运行 `pnpm nocobase db repair` 对齐（纯格式变化，符合 repair 的用途）。种子 004 已在开发库执行。
- 真实 GitHub 未联调（测试用假客户端；开发库未配置令牌与 webhook secret）。CI 状态只取 combined status 与 check suites，不看单个 check run。
- AI 解析器未在真实 LLM 上跑过（本机 `ai.llmServices` 为空）；Agent 以录入者 id、`roles: []` 运行，没有读数据的工具，也不需要。
- 手动关联已合并的 PR 不会触发合并流程；webhook 不会因 PR 标题改变而解除已有关联。
- 审批只支持单人决定（任一审批人批准即生效），没有会签 / 或签配置；请求取消不写活动。
- `env_changed` / `skills_changed` 活动未写（没有任务可挂）；环境变量有审计，技能没有变更记录。
- 被撤回（软删除）的任务仍会出现在已有的收件箱项里（点开 404）；订阅关系保留。
- `project.service.ts`、`protocol.ts` 仍超过 500 行（迭代 1 已超）；`protocol.phase1-iter2.ts` 546 行。
